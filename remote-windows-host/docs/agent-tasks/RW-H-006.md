## Acceptance criteria — spec content (normative §9)
9.1 Scope: video only on the media channel; all control stays on TCP 47987;
    video never passes through signaling.
9.2 Port + lifecycle: Host listens on TCP 47988. Media connection is accepted
    only from a peer that completed pairing (same session key) over 47987.
    Handshake: Client connects → Host sends 16 random nonce bytes → Client
    replies `HMAC-SHA256(session_key, "rwh-media-v1|" || nonce)` (32 bytes) →
    Host compares against the session key(s) of currently paired sessions and
    replies 0x01 (accept) or 0x00 (reject + close).
9.3 Key derivation (exact byte formats, LE where binary):
    - `session_key` = hex(sha256("rwh-pairing-v1|" + code + "|" + host_name))
      (existing `core::PairingManager::deriveSessionKey`; quote the exact
      format from `core/pairing.cpp` in the doc).
    - `media_key(window_id)` = hex(sha256("rwh-media-v1|" + session_key_hex + "|" + window_id)) — 32 bytes, AES-256.
    - `nonce_prefix(window_id)` = first 8 bytes of sha256("rwh-media-nonce-v1|" + session_key_hex + "|" + window_id).
9.4 Framing, little-endian, per packet:
    magic u8 = 0x52 ('R'); version u8 = 1; stream_id u16 = first 2 bytes of
    sha256(window_id); flags u8 (bit0 = keyframe); frame_seq u32 (per stream,
    starts 0, wraps); payload_len u32 (ciphertext length = plaintext + 16
    tag); then AES-256-GCM ciphertext of the H.264 byte payload, tag
    appended. Nonce = nonce_prefix(8) || packet_counter u32 LE (per stream,
    starts 0). Max payload_len = 16 MiB; anything else = malformed.
9.5 Stream lifecycle: follows `WINDOW_ANNOUNCE` / `WINDOW_REMOVE` (sent on
    47987). On announce: host starts the stream and its FIRST packet MUST be
    a keyframe. On remove: host stops; client discards. After any media
    reconnect, the host re-sends a keyframe for each active stream.
    FPS gating happens host-side before encoding (FR-09); `STREAM_STATUS`
    stays on 47987.
9.6 Robustness: malformed magic/version/oversize → close media connection;
    client reconnects and re-handshakes; no retransmission logic (TCP is
    reliable + in-order); malformed input never crashes (plan FR-13).
9.7 Security: no pairing → no session key → handshake fails; per-window key
    separation; authenticated encryption; no control semantics on 47988;
    frame contents and keys are never logged.

## Acceptance criteria — golden vectors
Create `protocol/test-vectors/media/` containing:
1. `aes-256-gcm.json` — at least 3 vectors: (a) key = 0x000102...1F, nonce =
   0x0001...0B, empty AAD, 64-byte patterned plaintext; (b) key = 0xA5
   repeated, nonce = counter-style 12 bytes, ~1000-byte patterned plaintext;
   (c) 1-byte plaintext. Each vector: key, nonce, aad, plaintext,
   ciphertext, tag (all hex).
2. `key-derivation.json` — using code `RWH-DEADBEEF` and host_name `TESTHOST`
   (synthetic, not a real secret): the expected `session_key` hex, and the
   `media_key` + `nonce_prefix` for a fixed window_id (use the UUID
   `11111111-2222-3333-4444-555555555555`). Compute them with the exact
   formats from `core/pairing.cpp` + §9.3 above (sha256 CLI or a short
   script).
3. A header comment / README in the dir: generator tool + date, and the rule
   that every AES-GCM implementation (CNG, CryptoKit) must reproduce these
   vectors exactly.

Vector generation: use a trusted reference implementation available on this
Mac (check `python3 -c "import cryptography"`; otherwise a small Swift
program using CryptoKit — `swift` is available via CLT). VERIFY each vector
with a second independent method if possible (e.g. generate in Swift, verify
in Python, or vice versa); record the exact verification commands and their
output in your report.
