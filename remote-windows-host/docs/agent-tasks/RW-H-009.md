# RW-H-009 — Win32 catalog source + allow-listed launcher + app wiring (H-CATALOG)

## Outcome
Implement the Windows-only catalog adapters on top of the merged RW-H-008
services: `StartMenuSource` (IShellLinkW scan of the per-user and all-users
Start Menu), `Win32Launcher` (allow-list-validated `ShellExecuteExW`),
`Win32ProcessProbe` (OpenProcess liveness), wire them into the GUI app and
extend `--selftest` with a fake-backed catalog+launch exchange, with
Win32-only unit tests that prove parsing, allow-listing, and a real
notepad launch/kill cycle on the Windows runner.

## Design notes (follow this; refine details, not the shape)

### StartMenuSource (`win32/catalog/`)
- `StartMenuSource(std::vector<std::wstring> roots = {})`. Default roots:
  per-user `%APPDATA%\Microsoft\Windows\Start Menu\Programs` and
  all-users `C:\ProgramData\Microsoft\Windows\Start Menu\Programs`.
  The constructor parameter exists for the unit tests (temp-dir roots).
- `scan()`:
  - Per-call COM: `CoInitializeEx(nullptr, COINIT_MULTITHREADED)`;
    treat `RPC_E_CHANGED_MODE` as "already initialized" and do NOT
    `CoUninitialize` in that case (standard pattern; scan may run on any
    session worker thread).
  - Recursively walk each existing root for `*.lnk` with FindFirstFileW/
    FindNextFileW (subdirectories; skip entries with HIDDEN or SYSTEM
    attribute; depth cap ~10).
  - Parse each `.lnk`: `CoCreateInstance(CLSID_ShellLink, ..., IID_IShellLinkW)`
    → `IPersistFile::Load` → `IShellLinkW::GetPath` (MAX_PATH,
    `FILENORMALIZELONGPATH`) → target; `GetDescription` → description.
  - Mapping to `core::CatalogRecord`:
    - `launch_target` = the full `.lnk` path (UTF-8);
    - `display_name` = description if non-empty, else the `.lnk` file name
      without extension, else the target's file name;
    - `identity_key` = `normalizeIdentity(display_name)` (REUSE core);
    - `source` = `"start_menu"`, `priority` = 10;
    - `available` = target looks like a drive path (`X:\...`) →
      `GetFileAttributesW != INVALID_FILE_ATTRIBUTES`; target is an
      `ms-appx:`/`ms-app://` URI → `true` (cannot verify offline; honest);
      GetPath fails (URL/link shortcut) → SKIP the entry (web links are
      not apps) — document this in a code comment;
    - `icon_ref` = `""` (MVP: client shows a placeholder; icons are a later
      task).
  - Return the merged record list; `CatalogService` handles dedupe (the
    same app present in both roots dedupes by identity_key).
- Never log scanned file names or paths beyond a count (structured log
  discipline; orchestrator logs `catalog.scan` with count + duration only).

### Win32Launcher (`win32/catalog/`)
- `Win32Launcher(std::vector<std::wstring> allowed_roots = {})` — same
  default roots as StartMenuSource (the allow-list IS the Start Menu).
- `launch(req)`:
  1. Convert `req.launch_target` (UTF-8) to wide.
  2. Validate, in order — failure returns immediately (launcher NEVER
     executes):
     - ends with `.lnk` (case-insensitive) → else
       `LaunchOutcome{false, "unauthorized", "Launch target is not an allow-listed shortcut"}`;
     - path exists (`GetFileAttributesW` file) → else
       `{false, "launch_failed", "The launch target no longer exists"}`;
     - the path is under one of `allowed_roots` (prefix match on the
       normalized wide path) → else the same `unauthorized` outcome.
  3. `SHELLEXECUTEINFOW` (`fMask = SEE_MASK_NOCLOSEPROCESS`,
     `lpFile = target`, `nShow = SW_SHOWNORMAL`) → `ShellExecuteExW`.
     Success with `hProcess` → `pid = GetProcessId(hProcess)` (0 possible
     for some launches → pid 0 = unknown, still `ok=true`);
     success without → `pid = 0`.
  4. Failure → `{false, "launch_failed", "The application could not be started"}`.
     safe_message is a stable generic string — never the raw OS error,
     never the path.
  5. `CloseHandle(hProcess)` after use (NOCLOSEPROCESS means WE own it).
- No arguments, no working-directory overrides, no elevation: the shortcut
  itself is the unit of launch (FR-02).

### Win32ProcessProbe (`win32/catalog/`)
- `isAlive(pid)`: `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, FALSE,
  pid)`; if it fails → return `true` (conservative: access-restricted
  running processes must not produce false `closed` events — document
  this); else `GetExitCodeProcess`: `STILL_ACTIVE` → alive, else dead.
  Close the handle.

- `add_library(rwh_win32_catalog STATIC win32/catalog/*.cpp)`;
  `target_link_libraries(rwh_win32_catalog PUBLIC rwh_core ole32 shell32)`;
  link it into the existing `rwh-host` target.
- `tests/CMakeLists.txt`: WIN32-only block for

- The two test TUs must NOT be added to the portable test lists (they must
  not compile on macOS).

### AppController wiring (ORCH-granted scope)
- `runGui` (Win32-only path): construct `StartMenuSource`, `Win32Launcher`,
  `Win32ProcessProbe`, `core::CatalogService`, `core::LaunchService`,
  `app::ControlServices{catalog, launch}`; pass the `ControlServices*` to
  `SignalingSessionHandler`. Log `catalog.ready` (entry count + revision +
  duration_ms — no names, no paths).
- `runSelftest`: same services but backed by IN-MEMORY FAKE
  implementations (three deterministic synthetic entries — e.g. names
  "File Explorer"/"Notepad"/"Access" with fake launch targets; compute
  their `app_id`s with `core::makeAppId` in-test; fake launcher: always
  ok, pid 4242; fake probe: always alive). Extend the selftest exchange
  after the existing pairing + `app_catalog_request`/`app_catalog`:
  - assert the received `app_catalog` has exactly 3 entries;
  - send `launch_app` with the first entry's `app_id` → expect
    `launch_result` state `started` + non-empty `application_session_id`;
  - send `launch_app` with `app-nope` → expect `launch_result` state
    `failed` + error_code `unknown_app_id`.
  - New machine-readable report keys (existing keys MUST stay):
    `catalog_entries` (int), `launch` (`started`|`failed`|`none`),
    `launch_unknown` (`rejected`|`missed`). `passed` requires the
    pre-existing conditions AND `catalog_entries==3` AND
    `launch=="started"` AND `launch_unknown=="rejected"`.
  - The selftest NEVER launches a real process (fakes only) — it must stay
    safe on any machine and deterministic for the runner.

## Acceptance criteria
- macOS side (verify here, report exact commands + exit codes):
  1. `cmake -S remote-windows-host -B remote-windows-host/build &&
     cmake --build remote-windows-host/build -j &&
     ctest --test-dir remote-windows-host/build --output-on-failure`
     → exit 0; all previously passing tests still pass (the portable
     baseline after RW-H-008), 0 failures. The new Win32 TUs/tests must
     NOT compile on macOS — if any portable build error appears, your
     WIN32 files leaked into the portable build.
  2. The Win32 code is written to compile on MSVC 14.51 / SDK 10.0.26100
     but you cannot run MSVC here — mark that NOT RUN (the orchestrator
     runs the Windows runner).
- Win32 tests (they run on the Windows runner by the orchestrator, but you
  must write them now):
  3. `startmenu_source_test`: temp-dir fixture built with IShellLinkW
     (create the .lnk files yourself: `SetPath` + `SetDescription` +
     `IPersistFile::Save`) under two roots; asserts: entries parsed with
     correct display_name (description fallback + filename fallback),
     `available` true/false per target existence, cross-root dedupe to one
     record via identity_key, app_id stability (scan twice → same app_ids),
     URL-only shortcuts skipped, hidden subdirectory skipped. Cleans up its
     temp tree (remove files + directories).
  4. `win32_launcher_test`:
     - a `.lnk` OUTSIDE the allowed roots → `ok=false`, `unauthorized`,
       and (crucially) no process was started (no assertion possible
       beyond the return value — note this in the test comment);
     - a non-`.lnk` launch_target (e.g. the temp .lnk's directory) →
       `ok=false`, `unauthorized`;
     - an allow-listed `.lnk` whose target was deleted → `ok=false`,
       `launch_failed`;
     - REAL launch: temp `.lnk` → `%SystemRoot%\System32\notepad.exe`,
       under a temp allowed root → `ok=true`, `pid>0`, probe alive →
       `TerminateProcess(pid, 1)` + `WaitForSingleObject` → probe dead.
       (Deliberate side effect on the dev runner: notepad opens briefly
       and the test kills it by PID — never `taskkill /IM`.)
  5. Selftest contract: on the runner, `rwh-host.exe --selftest` prints
     the extended JSON with `catalog_entries:3`, `launch:"started"`,
     `launch_unknown:"rejected"` and exit 0 (orchestrator verifies; you
     define the shapes so they are deterministic).

## Known risks
- SDK 10.0.26100 quirks: record any API discrepancy you find (plan rule 2)
  in your report; do not silently work around undocumented behavior.
- `app/Win32Env.hpp`: include it instead of `<windows.h>` in your Win32
  TUs; when in doubt include core headers first (its header comment
  explains).
- COM threading: scan runs on a per-connection worker thread (not STA) —
  the `RPC_E_CHANGED_MODE` pattern above is mandatory.
- The selftest runs on the runner under a non-interactive SSH session:
  keep it dependency-free (no display, no real processes).
- Notepad path: `%SystemRoot%\System32\notepad.exe` — verify with
  GetModuleFileNameW-style existence checks in the test before launching;
  if missing on the runner, the test must FAIL LOUDLY (report NOT RUN is
  for orchestrators, not tests).
