# RW-C-004 — Client shortcut adaptation: rules, translator, settings (C-INPUT)

## Outcome
Implement the macOS Client's FR-08 shortcut-remapping layer as a
dedicated, fully unit-tested module: physical-key code mapping
(macOS virtual key codes → Windows VK codes), the 16 built-in mappings
with the plan's exact default states, a versioned custom-mapping store,
a rule validator, the `KeyboardEventTranslator` (ordered Windows
key-down/key-up emission with correct modifier ordering), and the
**Keyboard Shortcuts** settings UI (master toggle, per-mapping toggles,
custom mapping editor) with L10n strings.

SCOPE NOTE (plan dependency gate): this task ships the adaptation
MODULE + settings + tests. The input pipeline integration — applying
rules "only while a remote window is the active input target" (FR-08
8.1) and emitting the resulting events as protocol `input_event`
`input_key_down`/`input_key_up` — requires the window-tracking
(C-WINDOWS) and host input pipeline (H-INPUT) stages, which come later
per the plan's dependency graph. This task must expose a clean,
tested integration seam (a pure function/protocol the future input
pipeline calls) and document it; it must NOT invent an input pipeline
or start forwarding keystrokes.

## Requirements (FR-08, plan §6.4)
- 8.1: match on PHYSICAL key codes + modifier flags (never localized
  character strings); a matching rule emits the target combination as
  ORDERED Windows key-down/key-up events with correct modifier-down
  BEFORE the key and modifier-up AFTER in reverse order; no match →
  passthrough decision (baseline translation, implemented by the future
  input pipeline — the translator returns a `passthrough` decision, not
  a dropped event); matching custom rule takes precedence over built-in;
  all rules deterministic and tested; reset outstanding key state on
  focus loss/connection loss (the seam must expose a `reset()` the
  future pipeline calls).
- 8.2: the exact 16 built-in mappings with defaults (transcribed from
  the plan — implement this table verbatim; rule IDs are stable,
  non-localized identifiers):
  | ID | macOS trigger | Windows target | Default |
  |---|---|---|---|
  | copy | Cmd+C | Ctrl+C | on |
  | cut | Cmd+X | Ctrl+X | on |
  | paste | Cmd+V | Ctrl+V | on |
  | selectAll | Cmd+A | Ctrl+A | on |
  | undo | Cmd+Z | Ctrl+Z | on |
  | redo | Cmd+Shift+Z | Ctrl+Y | on |
  | find | Cmd+F | Ctrl+F | on |
  | save | Cmd+S | Ctrl+S | on |
  | open | Cmd+O | Ctrl+O | on |
  | newDoc | Cmd+N | Ctrl+N | on |
  | print | Cmd+P | Ctrl+P | on |
  | closeDoc | Cmd+W | Ctrl+W | on |
  | quitApp | Cmd+Q | Alt+F4 | off |
  | refresh | Cmd+R | Ctrl+R | off |
  | newTab | Cmd+T | Ctrl+T | off |
  | saveAs | Cmd+Shift+S | Ctrl+Shift+S | off |
  Windows targets use the VK constants from the pinned protocol types
  (C=0x43, X=0x58, V=0x56, A=0x41, Z=0x5A, Y=0x59, F=0x46, S=0x53,
  O=0x4F, N=0x4E, P=0x50, W=0x57, R=0x52, T=0x54, F4=0x73 — VERIFY each
  against `ProtocolTypes.swift` / the snapshot before hardcoding; plan
  rule 2). Modifier mapping: Cmd (macOS) → the rule's declared Windows
  modifiers (Ctrl/Alt/Shift) — Cmd itself never maps to a Windows
  modifier for typing purposes in this MVP.
- 8.2 settings UI: master toggle ("Adapt macOS shortcuts for Windows"),
  a toggle per built-in mapping, visible source + target shortcut for
  each rule, and the plan-mandated one-line explanation that macOS
  global shortcuts may be intercepted by the OS and remain local.
- 8.3 custom mappings: a separate list where the user creates / edits /
  enables-disables / reorders / deletes rules; each rule = source
  (captured macOS key + modifiers), target (Windows VK + modifiers),
  enabled state, user label; MVP scope = global (per-application scope
  deferred — document in the UI/help text per the plan). Validation:
  reject empty mappings and unsupported combinations; detect duplicate
  source combinations and show a clear validation message (never
  silently pick an arbitrary rule); show the source+target preview
  before saving. Persistence: the versioned settings model (Client
  only — NEVER on the host); built-in defaults remain separately
  identifiable from custom rules (updating built-in defaults must never
  overwrite custom rules).
- Plan rule 15 / FR-14: all visible strings via L10n keys; rule IDs and
  key codes are stable machine identifiers, never localized.
- C-INPUT role constraint + FR-08 8.3 (plan lines 64, 253, 322): do NOT
  claim OS-reserved/global shortcuts are interceptable; the settings
  explanation is the honest statement.

## Design notes (follow the FR-08 §8.4 architecture; refine details)
- `ShortcutAdaptationService.translate(keyCode:modifierFlags:) ->
  Decision` — the public seam. `Decision` is either
  `.adapted([WindowsKeyEvent])` (the full ordered down/up sequence for
  the matched target: all target modifier downs, key down, key up,
  modifier ups in reverse) or `.passthrough` (no rule matched / master
  off / rule disabled). Pure function of (event, active rules, master
  toggle) — no I/O, trivially unit-testable. `reset()` clears any
  in-flight modifier state the service tracks.
- `BuiltInShortcutCatalog`: the 16-rule table above with default
  enabled flags; `id`, macOS trigger (keyCode + modifier flags),
  Windows target (VK + modifiers), `defaultEnabled`. Rule IDs are
  stable identifiers (the `ID` column above — refine if clearer, but
  never localized).
- `CustomShortcutStore`: persists to `Preferences` under a versioned
  schema (`version: Int` + rules array); loading an unknown/harder
  version → keep the stored data untouched + report (honest failure,
  like the existing preferences handling); saving bumps nothing if the
  schema is unchanged. Custom + built-in enable states are stored
  SEPARATELY (built-in toggles: per-ID overrides; custom rules: full
  list) so future default revisions never clobber user state.
- `ShortcutRuleValidator`: typed errors — empty trigger, empty target,
  modifier-only trigger (no key), unsupported/unknown VK, duplicate
  source combination (across custom rules and against enabled built-ins
  — report the conflicting rule name via an L10n key).
- `KeyboardEventTranslator`: builds the ordered event sequence for a
  matched target (modifier ordering per 8.1) — pure, table-driven.
- Settings UI (`KeyboardShortcutsSettingsView`, AppKit): master
  toggle at top; built-in section (one row per mapping: name via L10n,
  source shortcut text, target shortcut text, toggle); custom section
  (ordered list, add/edit via a capture field for the source shortcut +
  target picker, delete, up/down reorder, enabled toggle); the
  plan-mandated interception-explanation text (FR-08 8.2 + plan line
  753: a notice that system-reserved shortcuts may remain local); validation messages from
  `ShortcutRuleValidator` shown, never swallowed.
- Integration seam (for the later input-pipeline stage): the service +
  translator are Foundation-only; the future `InputRouter` (C-INPUT,
  later stage) will call `translate` while a remote window is the active
  input target and emit the `.adapted` sequence as `input_event`
  frames. Document this seam in a header comment on
  `ShortcutAdaptationService`. Do NOT wire any key forwarding in this
  task.

## Tests (Foundation-only, no display needed)
1. Built-in catalog: all 16 rules present with the EXACT table above
   (triggers, targets, default states); every rule ID unique; every
   target VK verified against the snapshot's VK constants.
2. Matching + precedence: each enabled built-in matches its trigger
   (physical codes + flags); a custom rule with the same source
   overrides the built-in; a disabled built-in (toggle off) does not
   match even with no custom rule; master toggle off → every trigger
   returns `.passthrough` without deleting stored rules; unknown
   trigger → `.passthrough`.
3. Emission ordering: for a multi-modifier target (e.g. saveAs →
   Ctrl+Shift+S), the adapted sequence is exactly [Ctrl down, Shift
   down, S down, S up, Shift up, Ctrl up]; single-modifier and
   Alt+F4 (quitApp) sequences pinned as literal event arrays;
   key-up events always paired with their downs.
4. Validator: empty trigger → typed error; modifier-only trigger →
   typed error; unknown VK → typed error; duplicate source (custom vs
   enabled built-in AND custom vs custom) → typed error naming the
   conflict; valid rule → no error.
5. Store versioning: round-trip (save → load → equal); built-in toggle
   overrides persist separately from custom rules (change one, the
   other is untouched); loading a future version → stored data
   untouched + honest report; master toggle persisted.
6. L10n: every new user-visible string resolves (extend the existing
   L10n suite pattern — keys for the section title, master toggle,
   per-rule display, explanation text, validation messages).
7. `reset()`: in-flight state (if any is tracked) is cleared;
   translate after reset behaves as a fresh service.
8. Existing suites stay green; record the exact before/after
   `swift test` check counts.

## Risks / known unknowns
- Settings UI rendering cannot be visually verified headless (CLT):
  unit-test the model + L10n; label UI rendering as NOT RUN.
- The plan's dependency graph places the combined H-INPUT + C-INPUT
  stage AFTER C-WINDOWS: if the orchestrator reorders, the integration
  seam must still be the only input-path surface.
- macOS virtual key code values (kVK_*) come from
  `macosx/CarbonHIToolbox/Events.h` via the CLT SDK — verify the
  constants used for C/X/V/A/Z/F/S/O/N/P/W/R/T/Q + modifiers against
  the CLT header (plan rule 2); if the header is unavailable under the
  CLT build, define the table with named constants + comments citing
  the header names (never magic numbers without a name).
- Cmd+Q → Alt+F4 and other "destructive" mappings default OFF per the
  plan — do not "improve" the defaults.
