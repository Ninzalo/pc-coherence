# RW-C-002 — Client catalog UI with launch (C-CATALOG)

## Outcome
Turn the macOS Client's honest "N applications" label into a real FR-01/
FR-02 catalog: a searchable, sorted entry list with availability display,
a Launch action per entry, per-app launch lifecycle state (from
`launch_result` + `app_status`), and `app_catalog_changed` handling
(re-request on change). All in the existing AppKit-only style, all
user-facing strings via L10n keys, core behavior unit-tested with the
fake-transport pattern.

## Requirements
- FR-01: display catalog (name, availability indication, launch state);
  search; sorting; icons (host sends `icon_ref = ""` in the MVP — render a
  neutral placeholder, never fake icons); launch state per entry.
- FR-02: launch by `app_id` only (the client NEVER sends paths/commands);
  launch states `accepted/starting/started/window_detected/failed`;
  process start vs window appearance are separate events (the client shows
  what the host reports — `started` stays `started` until the host says
  more; do not invent `window_detected`).
- Plan rule 6: every control performs a real action (no decorative UI).
- Plan rule 15 / FR-14: English-only strings via L10n keys; stable machine
  IDs (app_id, enum names) never localized.
- PROTOCOL v0.1.0 (pinned snapshot in `Protocol/Contract/`): `launch_app`
  requires `request_id` while paired; `launch_result` echoes it;
  `app_status` and `app_catalog_changed` are plain host→client kinds.

## Dependencies (already merged on the host side — the contract is stable)
- Host RW-H-008 (merged): paired `app_catalog_request` → REAL `app_catalog`
  (`catalog_revision >= 1`; entries have app_id, display_name,
  type, icon_ref, available). `launch_app` (known, available app_id) →
  `launch_result` `state=started` + 36-char `application_session_id`;
  unknown app_id → `failed` + `unknown_app_id`; unavailable → `failed` +
  `launch_failed`; launcher failure → `failed` + typed error. Host also
  sends `app_catalog_changed` (on catalog revision change) and
  `app_status` (`running`/`closed`) piggybacked on heartbeats.
- Client RW-C-001 (merged): `SignalingClient` state machine, `onCatalog`,
  `requestCatalog(forceRescan:)`, auto catalog request on pairing, 5 s
  heartbeat, fake-transport test pattern.
- No protocol change needed. No new dependencies (AppKit + Foundation only).

## Design notes (follow this; refine details, not the shape)

### SignalingClient (C-CONNECTION surface, granted)
- `@discardableResult public func launchApp(appID: String) -> Bool` —
  sends `launch_app` (fresh request_id, like `requestCatalog`) ONLY while
  `.paired`; returns false otherwise. No retry logic, no auto-resend
  (FR-02 / plan §5.2).
- New optional callbacks, delivered on the same queue contract as
  `onCatalog`: `onLaunchResult: ((LaunchResult) -> Void)?` and
  `onAppStatus: ((AppStatus) -> Void)?`. Handle the corresponding envelope
  kinds in the existing decode path (they already decode — verify the
  codec covers `launch_result`/`app_status` end to end via the vector
  suite; if a kind is missing from the CLIENT codec, that is a BLOCKER to
  report, not something to half-fix).
- `app_catalog_changed` (currently a no-op with a TODO comment): re-request
  the catalog with `force_rescan = false` while `.paired` (the host
  answers with the fresh snapshot). Keep the TODO comment removed/replaced.
- Store nothing sensitive; `launch_result`/`app_status` payloads are
  non-sensitive and may be surfaced to the UI.

### Catalog UI (AppController, AppKit-only, matching the existing style)
- Replace the single `catalogLabel` count with a catalog section in the
  main window (keep the window the app's home surface; do not create a
  second top-level window in this task):
  - `NSSearchField` (L10n placeholder) filtering entries by
    case-insensitive substring on `display_name`;
  - an `NSTableView` inside an `NSScrollView` (~200 pt), sorted by
    `display_name` (localized-compare), one visible column minimum:
    Name; a Status column or per-row suffix showing availability + launch
    state (e.g. "Unavailable" dimmed; "Running" / "Started" /
    "Failed: <safe_message>");
  - a `Launch` button (L10n) enabled iff state == `.paired` AND the
    selected entry is `available`; clicking it calls
    `client.launchApp(appID:)`; if the call returns false, surface the
    state problem via the existing status label (no silent no-op — rule 6).
  - empty catalog: keep the existing honest empty message
    (`catalog.empty`) instead of the table (or a disabled empty state —
    your choice, but no fake rows).
- Per-app launch lifecycle (small model, e.g. `CatalogLaunchModel` in
  `RemoteWindowsApp/App/` or a file of its own):
  `idle` → (launch clicked) → `launching` → `started(sessionID)` |
  `failed(safeMessage)`; `app_status closed` → back to `idle` (the app
  can be relaunched); a new `launch_app` for the same app_id resets to
  `launching`. Updates arrive off the main thread — hop to main before
  touching the table (the existing code already documents the
  callback-queue contract; follow it).
- Reconnect behavior: on a fresh pairing the existing auto
  `app_catalog_request` refills the list; the launch model resets on
  disconnect (no stale "Running" after the socket dies — input-state
  discipline analog).
- Icons: `icon_ref` is empty in the MVP — use a neutral system image
  (e.g. `NSImage(named: NSImage.applicationIcon)`) or text-only rows.
  Do not fetch or synthesize per-app icons.

### L10n (new keys, English values)
At least: `catalog.search.placeholder`, `catalog.launch`,
`catalog.launching`, `catalog.started`, `catalog.running`,
`catalog.closed`, `catalog.failed` (with a `%@` slot for safe_message),
`catalog.unavailable`, `catalog.column.name`,
`catalog.column.status`. Follow the existing key naming style in
`Localizable.en.json`. The L10nSuite has a test that every key used
resolves — add your keys there (or extend the existing coverage pattern).

### Tests (fake-transport pattern, like SignalingClientSuite)
- `launchApp` while `.paired`: exactly one `launch_app` envelope sent,
  kind/app_id/request_id shape correct (assert on the encoded envelope via
  the codec, like existing cases).
- `launchApp` while unpaired/connecting: returns false, nothing sent.
- `launch_result` received (started + session id) → `onLaunchResult`
  fired with the decoded payload.
- `launch_result` failed + `unknown_app_id` → surfaced with error code.
- `app_status` closed → `onAppStatus` fired; the launch model (if it is
  core-testable) transitions started → idle.
- `app_catalog_changed` while paired → one non-forced
  `app_catalog_request` sent; while unpaired → nothing sent.
- Catalog model: filtering (case-insensitive substring), sorting,
  availability/launch-state transitions (idle→launching→started→idle on
  closed; failed keeps the message).
- Keep ALL existing tests green (185 checks baseline + your new ones).

## Out of scope
- Host-side catalog scanning/launcher (done, RW-H-008/009 on the host).
- Icon extraction/bundling. Multi-window/remote-window UI (C-WINDOWS).
- Keyboard shortcuts (C-INPUT). `.app` packaging. SwiftUI migration.
- Persisting the catalog or launch history (the host is the source of
  truth; in-memory only).

## Known risks
- AppKit on the Swift Command Line Tools (no full Xcode): the existing
  app already builds/runs this way (ADR-0001-client-build-system-swiftpm)
  — stay within the APIs the codebase already uses (NSWindow/NSTableView/
  NSSearchField are AppKit and fine under CLT).
- Thread contract: callbacks arrive on the transport queue; the UI hops
  to main (documented in SignalingClient.swift header). Do not change the
  callback delivery contract.
- The `NSTableView` data source must tolerate the catalog being replaced
  wholesale (`onCatalog` fires again) while a selection exists — reset or
  re-validate selection on catalog refresh.
