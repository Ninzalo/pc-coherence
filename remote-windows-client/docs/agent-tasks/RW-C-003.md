# RW-C-003 — Client media channel: receive, decrypt, decode, render (C-PERF)

## Outcome
Implement the macOS Client half of the one-window end-to-end media slice
(PROTOCOL §9, plan Stage 1): receive the Windows Host's media channel over
TCP port 47988 — the §9.2 handshake, per-window AES-256-GCM decryption with
the §9.3 derived keys, §9.4 framing parse/validate with per-stream
counters, and one video window surface (VideoToolbox H.264 decode →
Metal). All protocol-level media code lives in `RemoteWindowsCore`
(Foundation + CryptoKit + Network.framework ONLY, so it is unit-tested
with the established fake/loopback pattern); the decode/render surface
lives in `RemoteWindowsApp` (AppKit + Metal + CoreVideo + VideoToolbox,
Xcode-free/CLT build).

## Requirements
- PROTOCOL §9.2 (handshake): on pairing the client connects to
  `host:47988`, reads the 16-byte `host_nonce`, sends the 32-byte
  `HMAC-SHA256(key = raw session_key,
  msg = "rwh-media-handshake-v1|" + host_nonce_hex + "|" +
  client_nonce_hex)` (client generates its own random 16-byte nonce),
  reads the 1-byte result (`0x01` accepted / `0x00` rejected → close).
- PROTOCOL §9.3 (keys): reproduce the golden `key-derivation.json`
  EXACTLY (all three values: session_key, media_key, nonce_prefix), using
  lowercase-hex SHA-256 as specified in that file's `formulas` field.
- PROTOCOL §9.4 (framing): 13-byte header, little-endian fields —
  magic `0x52`, version `1`, `stream_id` u16, `flags` u8 (bit0 =
  keyframe), `frame_seq` u32, `payload_len` u32 (max 16 MiB); decrypt
  with the stream's AES-256-GCM (nonce = 8-byte stream nonce_prefix +
  4-byte little-endian per-stream frame counter; AAD empty; 16-byte tag
  appended to the ciphertext); `stream_id` = first two bytes of
  `sha256(window_id)` as a little-endian u16 (must match the host's
  `core::streamIdFor`; test the layout explicitly).
- PROTOCOL §9.6 (close semantics): malformed magic/version, oversized
  payload, bad GCM tag, or connection reset → close the media channel
  with a typed error; the signaling session is NOT affected.
- FR-09 (context only): this task does NOT implement the FPS gate (host
  side); do not add client FPS logic beyond what the decode pipeline
  naturally has.
- Plan rule 6: the video window must be a real NSWindow that renders
  decoded frames (no placeholder/dummy surface).
- Plan rule 15 / FR-14: English-only strings via L10n keys; stable
  machine IDs (window_id, stream ids, enum names) never localized.
- Content policy: session keys, media keys, nonces, and frame payloads
  are NEVER logged. Log at most: stream_id, frame_seq deltas,
  durations_ms, decode error counts.

## Design notes (follow this; refine details, not the shape)

### RemoteWindowsCore/Media (protocol-level, fully unit-tested)
- `MediaFraming`: `struct MediaHeader` (magic/version/streamId/flags/
  frameSeq/payloadLen) + `serialize() -> Data` (exact LE layout) +
  `parse(_ data: Data) -> Result<MediaHeader, MediaFramingError>`
  (short buffer, bad magic, bad version, oversized payload_len → typed
  errors). `let kMagic: UInt8 = 0x52`, `kMaxPayloadLen = 16 * 1024 *
  1024`. Also `streamID(forWindowID windowID: String) -> UInt16` (first
  two bytes of sha256(window_id), little-endian — implement from the
  PROTOCOL §9.4 formula; add a test pinning the layout with a known
  sha256 digest).
- `MediaKeys`: `sessionKey(code:hostName:) -> String` (hex),
  `rawSessionKey(...) -> Data`, `mediaKey(sessionKeyHex:windowID:) ->
  Data`, `noncePrefix(sessionKeyHex:windowID:) -> Data` — the exact
  §9.3 formulas. A `MediaKeysGoldenSuite` case asserts ALL three values
  equal `test-vectors/media/key-derivation.json` (read the file at test
  time like `ProtocolVectorSuite` does).
- `MediaAead`: per-stream `MediaStreamCipher` holding
  `AES.GCM.SymmetricKey` + `noncePrefix` + `frameCounter: UInt32`;
  `seal(_:)`/`open(_:)` producing/consuming ciphertext+tag with nonce =
  prefix(8) + counter(4 LE), counter incremented per frame; AAD empty.
  Tampered ciphertext or tag → typed failure (CryptoKit `open` throws —
  map to `MediaAeadError.tampered`).
- `MediaHandshake`: a `MediaChannel` (or `NWMediaTransport`) wrapping an
  `NWConnection` to `host:47988` — connect, read exactly 16 bytes
  (host_nonce), send exactly 32 bytes (HMAC via
  `HMAC<Insecure.SHA256>` with the RAW session key over the exact
  `rwh-media-handshake-v1|<host_hex>|<client_hex>` message), read 1 byte
  (0x01/0x00). Make the connect phase injectable (the tests run a fake
  server on an ephemeral 127.0.0.1 port; the production path takes
  host IP from the same connection settings as the signaling channel).
- `MediaStreamState`: per-window stream state — cipher, last frame_seq
  (gap detection: a gap is logged + the stream continues, per §9.4
  "resync on next keyframe" — no close on gap), registered vs removed
  windows. `register(windowID:)` derives media_key + nonce_prefix +
  stream_id; `remove(windowID:)` frees the state.

### SignalingClient (C-CONNECTION surface, granted — minimal)
- On pairing accepted, derive the session key (code just presented +
  `hostName` from the challenge — both already held by the client) and
  retain it as a read-only property (e.g. `mediaSessionKey: String?`
  hex). It is needed by `MediaHandshake`/`MediaKeys`. Never log it.
  Clear it on disconnect/reset. Do NOT touch anything else in the state
  machine.

### RemoteWindowsApp/Video (surface — code-review verified; runtime NOT RUN headless)
- `VideoSurfaceView`: one `NSWindow` per window_id hosting a
  `CAMetalLayer`; a `CVTextureCache` for the decoder output.
- `VideoPipeline`: one `VTDecompressionSession` per stream (H.264,
  `kCMVideoCodecType_H264`); feed decrypted NAL payloads; on
  keyframe flag set, ensure the session can start decoding (flush on
  stream re-registration). Render callback → draw the texture into the
  window's layer.
- `AppController` wiring: on pairing → open the media channel (handshake)
  + `MediaStreamState` ready; on `window_announce` (control kind —
  already decoded by the client codec) → `register(windowID:)` + open
  the video window (title = announced title via L10n-safe rendering); on
  `window_remove` → remove stream + close window; on
  disconnect/reset → close channel + all windows,
  reset state (honest empty state, like the catalog). Note:
  `app_catalog_changed` (the existing catalog kind) does NOT
  affect media windows — do not wire a handler for it here.
- Because the host media server does not exist yet, `window_announce`
  will not arrive in production until a later host task — the wiring is
  verified by code review + the AppController unit paths; do NOT add a
  fake "demo stream" to the UI (plan rule 6: no decorative behavior).

## Tests (all 127.0.0.1 / ephemeral ports, fake/loopback pattern)
1. `MediaFramingSuite`: exact serialized header bytes for a known field
   set (pin the LE layout in a literal byte array); parse round-trip;
   reject short buffer, bad magic, bad version, oversized payload_len;
   16 MiB boundary accepted / 16 MiB + 1 rejected; `streamID(forWindowID:)`
   layout test (assert it equals the first two sha256 bytes reassembled
   little-endian — compute sha256 in-test).
2. `MediaKeysSuite`: all three `key-derivation.json` values reproduced
   exactly (session_key, media_key, nonce_prefix) from the golden
   inputs; malformed session-key hex input → typed failure.
3. `MediaAeadSuite`: for EVERY vector in `aes-256-gcm.json` — seal with
   the vector's key/nonce and assert ciphertext AND tag byte-exact; open
   the vector's ciphertext+tag and assert plaintext byte-exact; tampered
   ciphertext byte → typed failure; tampered tag byte → typed failure;
   counter increments per frame (two seals with the same key/prefix
   differ).
4. `MediaHandshakeSuite`: in-test fake media server (NWListener,
   ephemeral 127.0.0.1 port): (a) correct session key → client completes,
   server sees the expected 32-byte HMAC (server computes it with the
   same key — proves the exact HMAC input format); (b) wrong session key
   → server replies 0x00 → client reports rejected and closes; (c)
   server sends only 8 of 16 nonce bytes then closes → client fails
   cleanly with a typed error (no crash/hang).
5. `MediaStreamSuite`: full loopback: handshake OK, then the fake server
   sends N framed+encrypted payloads on TWO stream_ids (one starting
   with the keyframe flag, correct per-stream counters) → client
   decrypts, validates, routes by stream_id, delivers per-stream frames
   in order with correct counts; then a malformed frame (bad magic) →
   client closes the channel with a typed error while the signaling
   session stays connected.
6. `VideoPipeline` (construction only): create a
   `VTDecompressionSession` + `CMVideoFormatDescription` for H.264 from
   a minimal valid SPS/PPS fixture (hardcoded bytes in the test) and
   assert the objects construct; do NOT assert pixels (headless CLT —
   report pixel verification as NOT RUN in the final report).
7. Existing suites stay green; total `swift run RemoteWindowsAppTests`
   check count grows by the new cases (record the exact before/after
   numbers; this tree runs its suites as a SwiftPM executable with a
   minimal harness — CLT has no XCTest — so the command is
   `swift run RemoteWindowsAppTests`, NOT `swift test`).

## Acceptance criteria
- `swift build` exit 0 (CLT, no Xcode) in the worktree;
  `swift run RemoteWindowsAppTests` exit 0 with ALL suites passing
  (record the exact check count before/after + the new suite names).
- Golden vectors (key derivation + all AES-256-GCM vectors) reproduce
  exactly — cross-language compatibility with the host CNG implementation.
- No changes to `Protocol/Contract/`, the protocol schema, or host code.
- No secrets in any log line (session/media keys, nonces, payloads).
- Report format (same as RW-C-002): STATUS / TASK_ID / REPOSITORY /
  WORKTREE_PATH / BASE_COMMIT / RESULT_COMMIT / CHANGED_FILES (with
  per-file line counts) / TEST_EVIDENCE (exact commands, exit codes,
  counts; NOT RUN items labeled honestly) / RISKS / NEXT_DEPENDENCY.

## Risks / known unknowns
- VideoToolbox decode + Metal rendering cannot be visually verified in
  the headless CLT environment (no display): construction is tested,
  pixel output is NOT RUN — label it so; the orchestrator may verify on
  the Mac mini display later.
- The host media server (capture/encode/send) does not exist yet — real
  end-to-end video lands when the host capture task (after H-WINDOWS)
  merges; loopback coverage here is the acceptance bar for now.
- `SignalingClient` session-key retention is a C-CONNECTION surface
  change: keep it to the minimal property + derivation (mirrors the
  RW-C-002 grant pattern).
- `window_announce` wiring cannot be exercised against a live host yet;
  keep the AppController paths unit-testable via the existing
  fake-transport/callback pattern.
